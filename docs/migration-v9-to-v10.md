# Migrating from architect-orb v9 to v10

v10 changes the shape of the image pipeline, and removes two parameters from `push-to-app-catalog` that
the orb has ignored for at least a major version.

If your repo's `.circleci/config.yml` is generated by `devctl gen circleci`, both are handled for you:
regenerate and the new shape appears. The rest of this document is for configs maintained by hand.

## `push-to-registries` no longer builds the image

In v9 one job did everything: lint, build every platform with `docker buildx` (emulating all but one under
QEMU), tag, push, and sign.

In v10 the build is a separate job, [`build-image`](job/build-image.md), run once per architecture on a
machine of that architecture. `push-to-registries` joins the resulting digests into a tagged index, signs
it and attests it.

The point is speed: a Dockerfile with real work in its `RUN` steps spends far longer on its emulated
architecture than on its native one, and that architecture is the whole critical path. The native jobs run
concurrently, so wall clock becomes the slower single build rather than the sum.

### Before

```yaml
- architect/push-to-registries:
    name: push-to-registries-release
    image: giantswarm/myapp
    requires: [go-build]
    filters:
      tags:
        only: /^v.*/
      branches:
        ignore: /.*/
```

### After

```yaml
- architect/build-image:
    name: build-image-amd64
    platform: linux/amd64
    resource_class: small
    image: giantswarm/myapp
    requires: [go-build]
    filters: &image-filters
      tags:
        only: /^v.*/
      branches:
        ignore: /.*/

- architect/build-image:
    name: build-image-arm64
    platform: linux/arm64
    resource_class: arm.medium
    image: giantswarm/myapp
    requires: [go-build]
    filters: *image-filters

- architect/push-to-registries:
    name: push-to-registries-release
    image: giantswarm/myapp
    platforms: "linux/amd64,linux/arm64"
    requires: [build-image-amd64, build-image-arm64]
    filters: *image-filters
```

Keep the `push-to-registries` job's **name** unchanged, so anything that already `requires:` it —
`sync-china-registry`, chart jobs, repo-owned jobs in `.circleci/custom.yml` — keeps resolving.

### Parameters that moved

These are now parameters of `build-image`. CircleCI fails config compilation on an unknown job argument, so
leaving one on `push-to-registries` is an immediate, named error:

```
build-context   dockerfile   provenance   hadolint   hadolint-config   push   cache   cache-ref
```

`push-to-registries` keeps `image`, `platforms`, `resource_class`, `tag-latest-branch`, `git-tag-prefix`,
`tag-suffix`, `force-public`, `registries-data`, `split-china-push`, `annotations`, `oci-labels`, `sbom`,
`sbom-cyclonedx` and `sign`.

If your config passes **none** of the moved parameters it will compile, and then fail at run time with
`no digest recorded for linux/amd64` — the merge refusing to publish an index with no contents. That
message points back here.

### Things to get right

- **`resource_class` must match `platform`, and a mismatch fails the job.** `arm.medium` for
  `linux/arm64`, `small` or `medium` for `linux/amd64`. There is no emulated fallback, so a platform
  CircleCI has no native class for (`linux/arm/v7`, `linux/s390x`, `linux/ppc64le`) can no longer be
  built.
- **`platforms` on `push-to-registries` must match the set of `build-image` jobs**, in both directions. A
  missing digest and an unexpected digest are both hard failures, deliberately: either one would otherwise
  publish an index quietly missing an architecture.
- **`split-china-push` and `force-public` must be set identically** on the build jobs and the publish job,
  or they disagree about which registries hold the digests.
- **Annotations split by scope.** `manifest:` annotations go on `build-image`; `index:`,
  `index-descriptor:` and `manifest-descriptor:` go on `push-to-registries`. Each job rejects the other's
  with an explanation.
- **Branch paths have no publish job.** With `push: false` there is no digest to join, so a
  validate-only branch path is just the `build-image` jobs. If a chart job on that path needs
  `.build_version`, set `persist-build-version: true` on exactly one of them — they run concurrently, and
  CircleCI refuses to attach a workspace two concurrent jobs persisted the same path into.
- **`.platforms` no longer drives the image build.** `go-build` still writes it, but the platform set is
  now the list of `build-image` jobs.
- **Enable untagged-manifest retention** on the target registries. Each `build-image` job pushes by digest
  with no tag, so a pipeline that fails between the build and the merge leaves untagged manifests behind.

### Staying on the single-job build

There is no way to keep it. The v9 code path is deleted rather than deprecated: keeping both would mean two
builds of the same image kept in sync by hand, which is what this change exists to remove. A repo that
genuinely wants one job can run a single `build-image` for `linux/amd64` plus a `push-to-registries` with
`platforms: linux/amd64` — two jobs, one architecture, no emulation.

## What to check

Search your `.circleci/config.yml` for these two keys:

```
ct_config
skip_conftest_deprek8ion
```

If neither appears, you are done — merge the version bump.

If either appears, **delete the line**. CircleCI fails config compilation on unknown job arguments, so
leaving it in place will break the `push-to-app-catalog` job on v10.

## Why they went

### `skip_conftest_deprek8ion` — ignored since v6.3.2

This controlled the `helm-conftest` step, which ran the third-party
[deprek8ion](https://github.com/swade1987/deprek8ion) rego policies to flag Kubernetes API deprecations.
The step was removed in v6.3.2 after a conftest upgrade made it incompatible with those policies.

It was not restored: the policy set has been unmaintained since 2021 and only covered deprecations up to
Kubernetes 1.22, while app-build-suite already runs kube-linter over the same manifests in the helm build
pipeline. The `conftest` binary has also been dropped from the architect, app-build-suite, and
app-test-suite images.

See [roadmap#4066](https://github.com/giantswarm/roadmap/issues/4066).

### `ct_config` — ignored since v9.0.0

This pointed at a chart-testing config file for the `helm-lint` step. That step was removed in v9.0.0
along with the whole `architect`-executor path, when packaging moved to app-build-suite.

**Your `ct-config.yaml` file does not need to change.** app-build-suite still reads chart-testing config,
via the `ct-config` key in `.abs/main.yaml` — most repos already configure it there, and that path is
unaffected. Only the orb parameter is gone.

## What is *not* changing

The `executor` parameter stays. It accepts only `app-build-suite` (also the default), so passing it is
already a no-op, but around 275 repos set it explicitly. It is now permanently retained rather than
deprecated — you can leave it in place indefinitely.
